Frage: After a service is recreated, justify with verifiable evidence why clients should reconnect through the service name rather than a cached container IP, and name the commands or observations that demonstrate the explanation.

Classic F1 50.0 % · Graph F1 66.1 % · Delta +16.1

Classic RAG

The application should handle reconnecting when a service container is replaced. - Verify whether the application reconnects through the service name. - The application uses an IP address instead of the service name. Expected solution pattern: Use the service name as hostname and the container port as target port.

GraphRAG

Compose service name cannot be reached --documented_in--> Docker Docs: Compose networking. Compose networking documents service discovery by service name on shared networks. Connection uses old container IP --may_be_caused_by--> Container IP is dynamic. Containers can receive a new IP address when recreated while the service name remains stable. Container IP is dynamic --solved_by--> Reconnect using service name. Applications should use the service name and reconnect when an old connection closes. Compose service name cannot be reached --may_be_caused_by--> Services are not on the same network. A service name is reachable only when the communicating containers share a network. Compose service name cannot be reached --may_be_caused_by--> Host port and container port are confused. Inside Compose, a service should use the target container port, not the published host port. Compose service name cannot be reached --affects--> Compose default network. Compose service discovery depends on services sharing a Docker network.
